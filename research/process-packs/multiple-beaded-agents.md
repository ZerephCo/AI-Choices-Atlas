## 1. What it is
"Multiple Beaded Agents (MBA) turns one or more AIs into a configurable project team that runs on top of [Beads](https://github.com/gastownhall/beads). You stay the Orchestrator; MBA pairs every executable Bead with a Doer and an Auditor in separate sessions, keeps the Bead as the human record, and stops only on a verified fix or accepted proof." A thin coordination layer on top of Beads — **not** a new task database, **not** a fixed pipeline, **not** a provider-discovery service, **not** a silent self-modifier, **not** a resident daemon. Three responsibilities only: Orchestrator (coordinates), Doer (makes), Auditor (challenges). MBA is **instruction-driven**: when the active AI reads the installed repo instructions or the MBA skill, that active session becomes the thin Orchestrator; it does not wake up by itself.

## 3. Features
- **Three-only responsibility model** — Orchestrator / Doer / Auditor; explicit refusal to add new "responsibilities" beyond those three.
- **Beads-as-record** — Bead comments are the normal human-facing record; `.mba-work` is optional supporting storage, not a second place to follow. As clarified in `c609eb3`, the launch receipt and the worker's useful role-attributed comment are the normal progress surface: no routine Orchestrator kickoff, no static/implicit-field repetition, and no prompt/transcript/bulky-evidence dumps in comments; useful bulky evidence belongs under the session's `.mba-work/` directory only when needed.
- **Convergence loop** — Doer produces → Auditor returns `ACCEPT` / `FIND` / `BLOCKED`; convergence requires a **verified fix or accepted proof**, not bare agreement, not elapsed time. §8 evidence-required: `ACCEPT` must carry non-empty `REASONS` and `EVIDENCE` (after `FIND`, an `ACCEPT` needs a changed artefact or `RESOLUTION: no-change-proof`).
- **§10 assignment contract** — every executable Bead records Bead · Stage · Responsibility · Organizational role · Session purpose · Task · Read · Produce · Acceptance · Authority and limits.
- **User-authority gate (Charter §11)** — pauses for an explicit user decision before source Git commit/push, `bd dolt push/pull`, deploy, external messages, credentials, destructive actions, or adoption of a reusable workflow change.
- **Multiline-safe Bead-field writer** + read-back verifier (§10 assignment-contract generator) — primitives package avoids heredoc / stdin pitfalls on Windows/PowerShell.
- **`mba init` / `mba status` / `mba upgrade --dry-run` / `mba upgrade`** — install + status + upgrade lifecycle; refuses with `rc=5` on Beads-version mismatch; refuses with `rc=7` on user-edited managed blocks (no silent overwrite).
- **`mba remove --dry-run` / `mba remove`** — preview + remove lifecycle for MBA-managed install content; refuses on user-edited managed content; preserves `.beads/` and `.mba-work/` because those hold project history; `--force` for edited content.
- **Explicit role actors** — `bd --actor "Orchestrator"`, `bd --actor "Doer"`, `bd --actor "Auditor"`; default-actor reliance is explicitly forbidden for AI work.
- **Atomicity rule on `bd update --claim`** — only for human hands; AI workers update via `bd --actor "<Role>" update ...` so the user is not falsely recorded as the actor.
- **OpenCode cold-start bootstrap** — when an MBA-managed repo is opened in OpenCode (or any host that loads `AGENTS.md` / `.agents/skills/mba/SKILL.md`), the active AI session becomes the thin Orchestrator and runs `bd version` + `python -m mba_runtime first-contact --cwd . --apply-setup` before doing any project work. The `--apply-setup` flag is the deterministic, runtime-assisted path: `first-contact` itself creates or updates the blocked `MBA setup` Bead (`mba,setup,human` labels, assigned to `Human`) and posts the structured setup question comment with explicit `--actor "Orchestrator"`; the CLI still returns `rc=4` so the Orchestrator stops before executable Beads or worker launches. MBA is instruction-driven, not a resident daemon.
- **Safe worker launch** — the full rich assignment belongs in the worker session's `prompt.md`; the launcher sends only a short plain pointer such as `Read .mba-work/<bead-id>/<session-name>/prompt.md and follow it.` In particular, PowerShell launch messages must not contain Markdown backticks, command examples or rich assignment text, because PowerShell can interpret and corrupt backticked text.
- **OpenCode self-run worker surface (NEW in `c609eb3`)** — OpenCode's built-in `task` tool, `General Agent` subagent, and other in-host delegation share the Orchestrator transcript and therefore do **not** count as MBA Doer/Auditor workers. The canonical Windows/OpenCode surface is a separate external `opencode run` process launched hidden/background via `Start-Process -WindowStyle Hidden`, with redirected stdout/stderr and the pre-output launch receipt; the documented local CLI options are `--dir`, `--model`, `--variant`, `--auto`, `--title`, and `--format`.
- **Observable worker launch receipt (`.mba-work/<bead-id>/<session-name>/launch.md`)** — written in the **same launch step** that captures the worker's PID or session id, and **before** any wait, tail, read, or acceptance of the worker's output (Bead comment, transcript, `result.md`, `report.md`). The launch step is **one logical block**: write `prompt.md`, launch hidden/background, capture PID/session id, **immediately** write `launch.md`, only then wait/tail/read/decide. Writing the receipt **after** any worker output exists is a refusal-grade error. Charter §10 + §11, `docs/mba/technical-flow.md`, the MBA RULES block in `mba_foundation/markers.py` and the MBA skill source all converge on this rule (introduced in `ea01352`, hardened in `208c376` "Fix hidden worker launch guidance", and tightened in `15bc1e8` "Surface hidden worker handoffs"). The receipt is the only portable proof a separate Doer/Auditor session actually ran, recording `Bead` + `Session name` + literal `Launch command shape` (short plain pointer only) + `PID or session id` (or `not_available` with reason) + `Start time (UTC)` ISO-8601 + `Model / AI resource` + `Prompt path` + `Log / result paths` + **`Windows UX`** (one-line note that the launch was hidden/background via `Start-Process -WindowStyle Hidden`, so empty desktop CMD windows are not the progress surface); when the host exposes transcript or session identity, also record the launched worker identity and the Orchestrator identity, and verify that output is tied to the launched worker and differs from the Orchestrator — **PID-only proof is insufficient when stronger host identity exists**. Missing / stale / unbound ⇒ Orchestrator marks the Bead `blocked` and never manufactures convergence. Paired with the fixed **`Worker-internal AI delegation`** line in every worker comment (records `none` or every inner LLM/session/subagent/tool delegation); that line describes only what the launched worker did *inside* its own session and never substitutes for the launch receipt.
- **Worker / Orchestrator identity binding (NEW in `15bc1e8`)** — when the host exposes transcript or session identity, the receipt records both sides; before accepting any worker output the Orchestrator verifies that the output identity matches the launched worker and does **not** match the Orchestrator. PID-only evidence is treated as insufficient when stronger host identity exists. A match with the Orchestrator, a mismatch with the launched worker, or PID-only proof when stronger identity is exposed is a refusal — the round must not converge.
- **Visible blocked/Human handoff for hidden/headless Orchestrators (NEW in `15bc1e8`, recovery fixed in `c609eb3`)** — a hidden, headless or non-interactive Orchestrator never asks a human decision only inside its hidden transcript. A human decision or invalid worker provenance triggers a structured Bead comment plus status `blocked`, assignee `Human`, and label `human`. For launch/resume failure or missing `report.md` / `comment.md`, the bounded sequence is wait → resume the same MBA-owned session → one clean relaunch with a fresh receipt written before new output is read; if output is still missing, the same blocked/Human handoff applies instead of leaving the Bead silently `in_progress`. The Bead handoff is the human-visible question surface; the empty desktop window is **not**.
- **Missing-report recovery via runtime `LaunchProvenance` (NEW in `15bc1e8`)** — `mba_runtime/external_dispatch.py` now ships a `LaunchProvenance` dataclass (`worker_session_id` / `worker_transcript_id` / `observed_session_id` / `observed_transcript_id` / `orchestrator_session_id` / `orchestrator_transcript_id` / `pid` / `host_exposes_identity`) with a `validate()` method that rejects output that matches the Orchestrator, cannot be tied to the launched worker, or relies on PID-only evidence when stronger host identity exists. `ExternalProcessSessionRunner._surface_failure` posts the visible blocked/Human handoff (structured Bead comment + `bd update … --status blocked --assignee Human --label human`) **only for these three trigger conditions in the public `15bc1e8` source**: non-zero worker exit (`proc.returncode != 0`), failed `LaunchProvenance.validate()`, or missing `working.md` / `report.md` / `comment.md`. Pre-launch refusals — `WorkspaceSafetyError` raised by `assert_no_destructive_bd_init` / `assert_path_inside`, and `UserAuthorityRequired` raised when the §11 gate returns a refused decision — propagate directly to the caller without going through `_surface_failure()`. - **MBA-owned worker cleanup (NEW in `4e0e04b` / mba-dy6)** — `mba_runtime/external_dispatch.py` is the **single** capture-and-cleanup surface for MBA-owned worker PIDs and session ids; cleanup is ownership-gated, fail-closed, and bound to the launch receipt at `.mba-work/<bead-id>/<session-name>/launch.md`; the launch receipt is the only portable proof of MBA ownership. `cleanup_mba_owned_worker` is invoked after every terminal state — successful worker completion, convergence, blocked handoff, timeout, failure, retry, or relaunch — and any matching MBA-owned worker that is still alive is killed. The ownership gate refuses to act on a record whose ownership cannot be tied back to the launch: the User's own Claude / OpenCode / Codex sessions in the same repo are recorded as `owner=user` (or omitted from the MBA-owned registry) and the cleanup helper refuses to touch them; identity binding rejects records that match the Orchestrator's own session or transcript and refuses PID-only cleanup when stronger host identity was available at launch; ambiguous ownership — no launch receipt, identity match to the Orchestrator, identity unbound to a launch, or a permission refusal from the kill primitive — becomes a blocked/Human handoff, never a force-kill; the runtime never escalates a permission refusal into a force-kill. - **Not a tracker / not a memory / not a governance layer** — distinct from §3 Beads (the database), §4 memory, §8 action governance; MBA is the *workflow* that uses them.
- **Not a resident daemon** — MBA is **instruction-driven**: it runs only when an active AI/tool reads the installed instructions (or the MBA skill) and follows them. The active session becomes the thin Orchestrator; MBA does not wake up by itself.
- **Not provider-discovery** — the user configures AIs; MBA does not pick models (it may offer read-only local checks when `.mba-work/.ai-resources.json` is missing).
- **Not a silent self-modifier** — adoption of a reusable workflow change requires user approval (Charter §11).
- **Not a fixed pipeline** — stages, roles, and session counts are dynamic, not fixed.
- **Auto-wiring gap** — recovery library + `mba-runtime resources` CLI exist but auto-wire into `drive_bead`'s dispatch loop is **not on by default** (roadmap P4/P6).
- **Orchestrator visualisation gap** — `audit-trail.jsonl` / `sessions.md` rendering for the Orchestrator is **not on by default** (roadmap P1).
- **Beads-version lock** — `bd 1.0.4` is the validated version; widening to `v1.1.0` requires revalidation + user approval.
- **Windows sync-guard** — `bd dolt push` may refuse in embedded mode when paths exceed `MAX_PATH`; offers `bd init --server` or non-git remote instead.
- **Path-length caveat for `mba-runtime` console script** — Windows `pip install --user` writes it to `%APPDATA%\Python\Python3XX\Scripts`, which is **not** on `PATH` by default; prefer the `python -m mba_runtime …` module form, which needs only a working `python` and the installed `mba_runtime` package.
- **Not a process killer for user sessions** — MBA never kills the User's own Claude / OpenCode / Codex sessions; cleanup is ownership-gated and fail-closed (the `MBAOwnedWorker.owner == "mba"` check, the identity-binding refusal, and the permission-refusal → `PROTECTED` path all converge on "leave the foreign session alone"); when ownership cannot be proven the runtime posts a structured blocked/Human handoff and stops — it never escalates a permission refusal into a force-kill.

Long diffs, pre-researched conclusions, old transcripts, or any bulky context the worker can read from Beads/files/URLs **must not** be pasted into the worker prompt (Charter §3 + §10, MBA skill source step 4, MBA RULES block). ## 6. Positioning
- **MBA** — a *coordination discipline* + small Python runtime that drives a Bead from `bd ready` to `bd close` via opposed Doer/Auditor sessions under an Orchestrator, with a hard user-authority gate and an instruction-driven cold-start bootstrap. The public repo holds the source; the target-project install is the MBA-managed content (manifest + MBA RULES + referenced docs + verbatim skill + OpenCode bootstrap), while `.beads/` and `.mba-work/` remain target-project state.
- vs **Spec Kit / OpenSpec (§13.1)** — those are *spec-driven dev kits*; MBA is *workflow governance around a Bead* (does not write specs).
- vs **BMAD-METHOD (§13.2)** — BMAD is an *agile method with agent personas*; MBA is the *opposed-hat discipline* that can wrap a BMAD Bead as a single executable unit.
- vs **Superpowers / anthropics/skills (§13.3)** — those are *skills + methodology* to drop into a host; MBA is the *outer workflow* that decides which hats wear which skills (and MBA ships its own `.agents/skills/mba/SKILL.md` for hosts that read it).
- vs **Beads (§3)** — Beads is the *durable task database*; MBA is the *process layer* on top of it. MBA explicitly refuses to be a second task database.
- vs **§2 orchestrators** — orchestrators (AgentWrapper AO, GasTown, …) own visible team/cockpit semantics; MBA is a thin, opinion-less coordinator that delegates authority to Beads + the user's session.
- vs **§5 loop factories** — loop factories (Ralph, autonomy loops, …) own the *keep-going-until-done* semantic; MBA owns *who reviews who before convergence*, not iteration cadence.
- vs **§7 agent runtimes** — agent runtimes host the loop and tool calls; MBA sits above them and wraps a Bead; MBA is not a runtime.
